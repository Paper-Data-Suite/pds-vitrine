## Audit authority and scope

When sources disagree, this audit follows the repository authority hierarchy:

1. accepted ADRs govern architectural decisions;
2. exact accepted runtime contracts govern implemented shapes and invariants;
3. current implementation and tests establish executable behavior;
4. implementation documentation describes current supported workflows;
5. the v0.1.0 audit register preserves historical findings and dispositions;
6. issue text describes work intent but does not rewrite preserved audit history.

The v0.1.0 findings register contains **PF-AUD-001 through PF-AUD-012**. Issue #40's
initial prose included an abbreviated PF-AUD-001–009 mapping whose descriptions do

## Architectural verdict

No runtime architecture blocker was found in the initial issue #40 audit pass.

The merged v0.2.0 implementation preserves the central authority chain:

```text
Core-compatible fixture publication
  -> canonical Core reload and source verification
  -> exact Vitrine development-fixture adapter selection
  -> explicit source-read authorization
  -> Candidate Evaluation
  -> Candidate
  -> explicit curation authority and Selection
  -> Placement / Arrangement / Reflection / Review
  -> immutable Working Portfolio Composition Revision
  -> exact Snapshot Build Request and Plan
  -> guarded source acquisition / deterministic rendering
  -> internal Manifest and Seal
  -> immutable Snapshot Edition
  -> independently verified directory Export Artifact
```

The implemented release subset remains fixture-backed. Live ScoreForm, Quillan, and
Concord integrations remain a follow-on concern and are not required to close v0.2.0.

### ADR 0001 — authority and dependency direction

The release keeps Core authoritative for workspace, roster, Academic Work,
Publication, compatibility, manifest binding, and discovery. Vitrine remains
responsible for Portfolio identity, Candidate policy, curation, Composition, and
Snapshot/Export custody. Producer-shaped fixtures retain their own synthetic
semantics. Meridian grading/proficiency, Portia behavior-support records,
institutional authorization, and external outcomes are not absorbed into Vitrine.

The following remain non-equivalent:

```text
Candidate != Selection
Selection != Placement
Selection != disclosure authorization
Audience Context != recipient/disclosure authorization
actor attribution != authorization
```

### ADR 0002 — identity

The implemented identity layer preserves one opaque workspace-scoped Portfolio
Subject across exact class-qualified references. Display name and bare local student
ID are never identity proof. Identity correction, merge, split, invalidation, and
supersession preserve history through explicit records rather than endpoint rewrites.

The installed acceptance strengthens this with three class/year contexts containing
one shared synthetic subject and a deliberately confusing same-display-name student.

### ADR 0003 — Profiles

Profile lifecycle and binding are explicit. Current authority is not derived from the
largest revision or newest timestamp. A Portfolio binds one exact activated Profile
Revision, and migration is an explicit successor workflow.

The generic purpose vocabulary does not claim all purpose families are operational.
V0.2.0 exercises Improvement and Showcase only.

### ADRs 0004 and 0005 — discovery and producer exposure

The implemented trust sequence preserves catalog nonauthority, canonical Core reload,
exact compatibility, authorization, digest-bound manifest verification, strict fixture
reader parsing, exact projection identity, subject relationship, and Profile evaluation.

Vitrine-owned fixture identities are deliberately different from current public sibling
producer contracts. Live-like ScoreForm, Quillan, and Concord support requests cannot
select a Vitrine fixture adapter. The runtime does not crawl sibling storage or parse
undocumented private files.

ScoreForm-shaped attempts remain separate and unranked. Standards alignment does not
become proficiency. Concord-shaped Group Membership, Artifact Author, Artifact Subject,
documented contribution, and Score target remain distinct.

### ADR 0006 — curation

Curation history is append-preserving. Proposal, Decision, Selection, Placement,
Arrangement, Presentation, Rationale, Annotation, Reflection, Review, and Composition
retain independent identities and authority. Current Arrangement and Composition use
explicit pointer heads rather than incidental ordering.

Reflection remains actor-authored interpretation, not proof of improvement, proficiency,
consent, remorse, or compliance.

### ADR 0007 — Snapshot custody

The runtime preserves these distinct layers:

```text
Core manifest digest
producer source digest
acquired source digest
copied/generated Entry digest
internal Snapshot Manifest digest
logical inventory digest
Snapshot Seal
Snapshot Edition business identity
Current Edition pointer
Export directory inventory digest
```

`SnapshotState.current_edition()` resolves the explicit Current pointer and then resolves
that exact Edition. Issue #39 makes this discriminating by keeping Improvement Edition 1
current while a verified Edition 2 exists with the greater edition number.

Issue #39 also mutates/deletes staged source data, removes the complete producer-source
root, re-verifies three Editions and two Exports, and reloads history in a fresh isolated
interpreter without producer source. Issued history therefore does not silently refresh.

### ADR 0008 — privacy boundary

V0.2.0 implements enough privacy structure to keep the fixture-backed local slice safe:
explicit authorization gates, minimum-necessary fixture projections, bounded Audience
Contexts, collaborator review, no private producer fallback, and an actual Showcase
Export scan that excludes internal manifest/private/authorization markers.

It does not implement a production institutional authorization system. Recipient Scope,
consent, redaction/de-identification, Disclosure Authorization, delivery, and external
submission remain future work and must remain unclaimed in release documentation.

### ADR 0009 — regulated boundary

The generic Profile architecture can represent `purpose_kind = regulated`, but V0.2.0
does not activate operational regulated cases, checklists, attestations, submissions,
receipts, or outcomes. The New Jersey-style material remains research-only and
cohort-bound.

## Persistence and concurrency audit

The v0.2 canonical-state implementations preserve append-only or immutable domain
records and explicit head/pointer records. Current state is not inferred from maximum
revision or newest timestamp where an explicit authority chain exists.

The release audit specifically preserves:

- expected-revision protection and conflict-aware canonical commits;
- derived SQLite/catalog nonauthority;
- strict canonical reload and validation;
- append-preserving identity/Profile/curation/Snapshot history;
- explicit Profile, Arrangement, Composition, and Snapshot head/pointer resolution;
- conservative partial-success and uncertain-durability behavior;
- nonauthoritative diagnostics that do not repair by observation;
- lock handling that does not infer safety merely from age.

Final release qualification must verify that the complete validator leaves the working
tree unchanged.

## Privacy and documentation finding

### V02-AUD-001 — stale `Security.md` runtime description

**Severity:** documentation defect
**Release impact:** must be corrected before release

At the start of #40, `Security.md` still stated that the package only managed the shared
Core workspace and did not open producer manifests or student work. That description was
accurate for the package baseline but became stale after Candidate discovery, curation,
and Snapshot work.

Issue #40 corrects the statement to the actual v0.2 boundary:

- verified Core-backed **synthetic fixture** publications may be inspected only through
  explicit authorization and strict Vitrine-owned development projections;
- Vitrine can persist Portfolio/Candidate/curation state and build immutable local
  Snapshot Editions and directory Exports;
- the development fixtures are not live producer integrations;
- v0.2 remains not a production institutional authentication/authorization, consent,
  redaction/de-identification, delivery, hosting, or external-submission system.

No runtime behavior change is required for this finding.
