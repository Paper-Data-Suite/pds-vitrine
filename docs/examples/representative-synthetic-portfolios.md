# Representative Synthetic Portfolios

- **Status:** Foundation acceptance corpus
- **Fixture contract:** `pds-vitrine.representative-portfolio-corpus` version `1`
- **Runtime authority:** None; the fixture descriptor is not a public Vitrine schema
- **Data classification:** Synthetic only
- **Related issue:** #12, “Build representative synthetic portfolios”
- **Corpus root:** [`../../fixtures/representative-portfolios/`](../../fixtures/representative-portfolios/)
- **Validator:** [`../../scripts/validate_representative_portfolios.py`](../../scripts/validate_representative_portfolios.py)

## Purpose

The earlier Vitrine foundation documents define individual architectural contracts for:

- Portfolio and Portfolio Subject identity;
- versioned Portfolio Profiles;
- Candidate discovery and exact source references;
- producer artifact exposure;
- Selection, ordering, Annotation, and Reflection;
- immutable Composition Revisions;
- Snapshot Entries, manifests, checksums, Editions, and exports;
- privacy, authorization, redaction, and audience controls; and
- regulated Portfolio cases, checklists, attestations, approvals, submissions, and outcomes.

This corpus demonstrates that those contracts can form coherent Portfolio stories rather than remaining isolated examples.

Each positive fixture follows the same broad chain:

```text
exact synthetic identity
  -> exact Profile revision and Binding
  -> producer-shaped source records
  -> Candidate and Selection records
  -> explicit curation and Composition Revision
  -> audience and authorization records
  -> deterministic Snapshot Manifest
  -> actual copied or generated bytes
  -> immutable Snapshot Edition
  -> expected findings
```

The corpus also contains deliberate contract violations that the validator must reject with exact error codes.

## What this corpus is not

The corpus does not:

- define final Vitrine JSON Schema;
- implement a Vitrine application or persistence layer;
- import or execute sibling packages;
- prove that every illustrated producer projection exists at runtime;
- calculate improvement, proficiency, or Grades;
- choose an official ScoreForm attempt;
- convert Concord Group results into individual results;
- activate a New Jersey regulated Profile;
- authorize real recipients;
- or expose Portia records.

The descriptor files are development fixtures written to make foundation behavior reviewable and machine-checkable.

## Shared synthetic identity

All four positive Portfolios use one opaque synthetic student reference and one Portfolio Subject.

The subject is linked across three class-qualified references:

- synthetic English 10 in 2023–2024;
- synthetic English 11 in 2024–2025; and
- synthetic English 12 in 2025–2026.

The association explicitly records authoritative references plus human confirmation.

It is not based on:

- display name;
- repeated local `student_id` alone;
- email address;
- filename;
- or inferred chronology.

This allows the improvement Portfolio to demonstrate multi-year continuity without weakening the identity contract.

## Shared source artifacts

The corpus commits actual bytes for every source that may be copied into a Snapshot.

The source index records:

- stable synthetic source ID;
- workspace-relative path;
- producer or local owner;
- projection kind;
- visibility classification;
- byte size; and
- lowercase SHA-256.

The validator recomputes every source digest.

### Quillan-shaped sources

The shared Quillan-shaped sources include:

- an early argument draft;
- a revised argument;
- a polished literary analysis;
- separate student-facing feedback for the early and revised work;
- family-safe feedback; and
- a deliberately private teacher note.

Original work and feedback remain separate records and separate Portfolio Entries.

The private note is committed only as restricted test input. It never enters an audience package.

### ScoreForm-shaped sources

The ScoreForm-shaped attempt summary contains:

- one work identity;
- two attempts;
- native earned and possible points;
- an explicit `blank` question state;
- an explicit `ambiguous` question state;
- and declarations that no official attempt, Grade, or proficiency has been selected or calculated.

The corpus also contains separate synthetic secure material marked prohibited.

The secure material never enters a Candidate, Selection, Snapshot Entry, or audience package.

### Concord-shaped sources

The Concord-shaped source set contains:

- Activity, Session, and Group identity;
- Group Membership;
- Artifact identity;
- Group authorship;
- Portfolio Subject relationship;
- a specific contribution finding;
- a Group-targeted Score; and
- an audience-safe attribution projection.

The Group-targeted Score explicitly does not create an individual Score.

### Portia-shaped restricted source

The Portia fixture contains one minimal restricted source with a unique marker.

Its purpose is to prove deliberate exclusion and no-existence leakage handling.

The public Portfolio flows do not create:

- a Candidate;
- a Selection;
- a Placement;
- a Snapshot Entry;
- an audience-visible Omission notice;
- or an audience-visible diagnostic

for that source.

The validator scans every exported path and byte stream for the restricted marker and related IDs.

## Portfolio 1: Improvement

### Story

```text
English 10 baseline work and feedback
  -> English 11 revised work and feedback
  -> student comparison Reflection
  -> student-facing improvement Snapshot Edition
```

The fixture uses separate Candidates and Selections for:

- baseline work;
- baseline feedback;
- revised work; and
- revised feedback.

The explicit Arrangement places those records into baseline, baseline-feedback, later-work, and later-feedback sections.

A student-authored Reflection identifies the changes the student believes are meaningful.

### Important boundary

Vitrine does not calculate improvement.

The corpus preserves exact artifacts and an attributable comparison. It does not create a cross-assignment proficiency calculation, change score, or Grade.

### Audience output

The student-facing directory package contains:

1. baseline argument;
2. baseline feedback;
3. revised argument;
4. revised feedback;
5. student reflection; and
6. generated index.

The private Quillan note and suppressed Portia source remain absent.

### Immutability assertion

The Snapshot binds the exact baseline and revised source bytes selected by the Composition Revision.

A later producer revision cannot replace either source without a new Candidate/Selection path and a new Snapshot Edition.

- a proficiency level;

- the internal Snapshot Manifest; and

An audience label alone would not authorize delivery.

### Record-access boundary

The conference package is a purpose-limited Portfolio Edition.

It is not represented as a complete response to a formal education-record request.

## Portfolio 4: NJ-style regulated pathway

### Status

This fixture is explicitly research-only and non-operational.

It does not contain:

- an official NJDOE form;
- a real Statement of Assurance;
- a real data spreadsheet;
- a real student identifier;
- a real constructed-response task;
- a real signature;
- a real submission;
- or a real outcome.

### Story

```text
research-only regulated Profile revision
  -> synthetic regulated student case
  -> independent ELA and mathematics components
  -> explicit pathways and eligibility findings
  -> local supporting records and checklist findings
  -> attestation and local approval
  -> conditional readiness
  -> local review Snapshot
  -> school-level batch
  -> initial submission and receipt
  -> corrected submission and second receipt
  -> component-specific synthetic outcome
```

### Independent components

The ELA component uses a synthetic standard Portfolio pathway.

The mathematics component records that the requirement was satisfied through another pathway and is not part of the Portfolio submission.

ELA completion does not imply mathematics completion, and vice versa.

### Restricted-source activation boundary

The fixture records that restricted operational source review remains unresolved.

Consequently:

- the Profile remains research-only;
- operational activation is blocked; and
- readiness is only conditional within the synthetic scenario.

### Local file versus school batch

The local review Snapshot contains selected local evidence and a generated checklist summary.

The school submission directory separately contains:

- initial synthetic batch data;
- corrected synthetic batch data;
- first and second synthetic receipts; and
- one ELA-specific synthetic outcome.

The batch files are not the canonical student case.

The corrected submission points to its predecessor rather than overwriting it.

### External stages

```text
local checklist finding
  != local approval
  != readiness
  != submission
  != receipt
  != external outcome
```

The fixture preserves each stage separately.

## Snapshot and checksum model

Every positive Portfolio commits:

- one internal manifest;
- actual audience-package files;
- an exact manifest digest stored outside the manifest;
- an independently calculated logical-inventory digest;
- Entry-level SHA-256 digests;
- Entry byte sizes;
- deterministic Entry sequences;
- unique Entry IDs;
- unique workspace-relative paths; and
- exact source paths for byte-copy materialization.

The internal manifest does not include its own digest.

For an exact byte copy, the validator confirms:

```text
source bytes == exported Entry bytes
```

For generated content, the validator verifies the committed output bytes and digest without claiming a production renderer.

The directory package contains only declared audience Entries.

It does not contain the internal manifest.

## Validator behavior

Run from the repository root:

```powershell
python scripts/validate_representative_portfolios.py
```

The validator uses only the Python standard library.

It performs no network access and imports no PDS package.

It verifies:

- fixture contract and version;
- shared and Portfolio-local ID uniqueness;
- exact record references;
- artifact existence;
- source digest and size;
- safe workspace-relative paths;
- Snapshot identity bindings;
- manifest digest;
- deterministic Entry ordering;
- logical-inventory digest;
- Entry digest and size;
- exact byte copies;
- unique Entry IDs and paths;
- absence of undeclared audience files;
- absence of the internal manifest from audience packages;
- absence of forbidden private or suppressed markers;
- expected inclusion and exclusion sets;
- external regulated-artifact digests; and
- exact negative-case failures.

The expected successful result is:

```text
PASS representative Portfolio corpus: 4 portfolios, 20 Snapshot Entries, 20 negative cases, 39 verified byte files
```

## Security and privacy

All identities, educational content, scores, roles, documents, receipts, and outcomes are synthetic.

The corpus intentionally uses conspicuous markers for prohibited private content so accidental leakage is detectable.

Those markers appear only in restricted source fixtures and negative mutation payloads.

They must never appear in positive audience exports.

No file in the corpus provides legal advice, activates a regulated Profile, authenticates a real actor, or authorizes a real disclosure.
