This document freezes the intended Vitrine v0.3.0 package/runtime compatibility
boundary. It does not claim that a `v0.3.0` GitHub Release has already been
published.

## Fixture/live separation

Development fixture identities remain explicit and opt-in:

```text
vitrine_scoreform_fixture
vitrine_quillan_fixture
vitrine_concord_fixture
```

They are not aliases for released producers. Ordinary live adapter selection must
not choose them, and Core installed-producer discovery must not expose them as live
producer registrations.

## Source-read and Artifact authorization

The release preserves this source-read ordering:

```text
Core discovery
-> canonical Publication reload
-> canonical producer registration
-> series / withdrawal state
-> compatibility
-> source-read authorization
-> Core path/digest verification
-> immutable manifest bytes
-> public producer reader
-> pure Vitrine projection
```

Authorization precedes protected producer source content I/O.

For Quillan and Concord:

```text
source-read authorization != producer Artifact authorization
```

Copied bytes require the exact public producer Artifact boundary and an explicit
`allowed` result. `denied` or `unresolved` fails closed. Vitrine does not reconstruct
producer-native paths or use producer-private storage APIs.

## Portfolio and curation boundary

Operational local Profile workflows in v0.3.0 are:

```text
Improvement Portfolio
Showcase Portfolio
```

The release preserves:

```text
Portfolio != Portfolio Subject
Candidate != Selection
Selection != Placement
Selection != disclosure authorization
Reflection != proof of improvement / proficiency / consent
Working Composition != Snapshot
```

Cross-class Portfolio Subject identity is exact and history-preserving; display
name or a bare local student ID is never identity proof.

ScoreForm attempts remain independent. Vitrine does not choose the latest, highest,
best, official, Grade-bearing, or proficiency-bearing attempt. Standards references
do not become proficiency/mastery.

Concord Group Membership, Artifact Author, Artifact Subject, documented contribution,
represented Group, Score target, and Portfolio Subject remain distinct.

## Snapshot and Export custody

The release distinguishes:

```text
Selection != Snapshot build authority
Snapshot build authority != disclosure authorization
Snapshot Edition != Export Artifact
Current Edition != greatest Edition number
local directory_package Export != delivery
```

Build Plans freeze exact source and curation provenance. Sealed Edition and Export
verification is producer-independent after custody is established. Export tampering
must fail verification.

## Audience/privacy boundary

```text
Audience Context
!= recipient identity
!= recipient relationship
!= consent
!= disclosure authorization
!= delivery authority
```

Vitrine v0.3.0 can create a purpose-specific local Export. It does not send it.

Normal diagnostics, attention projections, and suite operations remain bounded and
must not emit raw manifests, student-work bodies, feedback bodies, answer keys,
private notes, authorization-provider prose, producer-native paths, or absolute
workspace paths.

Suppressed Candidate state must not leak through rows, counts, facets, hidden-result
messages, producer labels, attention totals, or placeholder records.

## Core suite-operations boundary

Vitrine exposes exactly:

```text
paper_data_suite.module_operations
  vitrine = vitrine.pds_operations:get_module_operations_profile
```

The provider adapts Vitrine-owned readiness and attention information into Core's
module-operations contract. It does not surrender Vitrine record authority to the
suite.

Class-scoped Vitrine attention remains unavailable where Portfolio-wide state cannot
be safely attributed to one class. Suite backup/restore operates on workspace bytes:

```text
suite backup != Snapshot Export
suite restore != Vitrine repair
restored bytes != permission to reinterpret or redisclose Portfolio content
```

## Deliberately outside v0.3.0

The release does not claim:

- production institutional authentication/authorization;
- recipient or guardian relationship verification;
- consent management;
- production redaction/de-identification or disclosure-event infrastructure;
- secure external delivery, public hosting, or submission automation;
- operational Parent/Guardian Conference or regulated Portfolio workflows;
- Meridian grading/proficiency policy;
- ordinary Portia Portfolio exposure; or
- suite-wide policy authority over Vitrine records.

Those are deferred surfaces, not v0.3.0 defects unless current code or documentation
falsely claims they exist.
