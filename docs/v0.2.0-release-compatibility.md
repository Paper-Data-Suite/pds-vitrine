# Vitrine v0.2.0 Release Compatibility Boundary

- **Issue:** #40
- **Audit date:** 2026-08-17
- **Starting implementation commit:** `67b8f0f57563397627958f7ff36d9c134081669c`
- **Audit-start package version:** `0.2.0.dev0`
- **Release source version:** `0.2.0`
- **Target release version:** `0.2.0`
- **Status:** release identity prepared; qualification/publication pending

This document freezes the intended Vitrine v0.2.0 package/runtime boundary. It is not a
claim that the `v0.2.0` release has already been published.

## Package identity

```text
distribution:                  pds-vitrine
import package:                vitrine
release version:              0.2.0
Python requirement:            >=3.11
Core runtime dependency:       pds-core>=0.6,<0.7
console script:                vitrine = vitrine.cli:main
paper_data_suite.modules:      not declared
publication_producers entry:   not declared
unconditional sibling deps:    none
```

The release must keep one authoritative version source in `vitrine/_version.py`.
Installed distribution metadata, `vitrine.__version__`, `vitrine --version`,
`python -m vitrine --version`, wheel metadata, and sdist metadata must agree.

## Supported interpreter matrix

Release CI covers:

```text
Ubuntu:  Python 3.11, 3.12, 3.13, 3.14
Windows: Python 3.11, 3.12, 3.13, 3.14
```

The current topology uses six compatibility cells and two complete-qualification corner
cells. This is equivalent platform/version coverage without eight duplicate expensive
qualifications.

## Runtime dependency boundary

The Vitrine wheel must have no unconditional runtime dependency on:

```text
pds-scoreform
pds-quillan
pds-concord
pds-portia
pds-meridian
```

Vitrine runtime code may depend on public `pds-core` contracts. V0.2.0 does not require
an installed producer package to execute its accepted fixture-backed Improvement and
Showcase qualification scenarios.

The package deliberately does not declare:

```text
paper_data_suite.modules
paper_data_suite.publication_producers
```

Adding either entry point is an architectural change, not release housekeeping.

## Development fixture identities

V0.2.0 owns three explicit synthetic producer identities:

```text
vitrine_scoreform_fixture
vitrine_quillan_fixture
vitrine_concord_fixture
```

Their fixture manifest/Academic Work/source contracts are Vitrine-owned test contracts,
not aliases for current live producer contracts.

The boundary rule is exact:

```text
live ScoreForm-like support request
    must not select vitrine_scoreform_fixture

live Quillan-like support request
    must not select vitrine_quillan_fixture

live Concord-like support request
    must not select vitrine_concord_fixture

Core installed producer discovery
    must not expose any Vitrine fixture producer identity
```

These are Vitrine-owned synthetic projections shaped to exercise producer semantics;
they are not live producer integrations.

## Ordinary fail-closed configuration

`default_workflow_dependencies()` is part of the release boundary.

It must continue to provide:

```text
empty PublicationProducerRegistry
empty ProducerProjectionAdapterRegistry
unresolved source-read authorization gate
unresolved curation authority gate
unresolved Snapshot-build authority gate
empty Snapshot source-provider registry
empty Snapshot renderer registry
UnconfiguredSnapshotPlanningProvider
development_fixture_mode = false
```

No fixture registry, permissive authorization decision, source provider, or renderer may
appear implicitly in the ordinary production context.

## Operational v0.2.0 Portfolio slices

The release claims executable local fixture-backed support for:

```text
Improvement Portfolio
Showcase Portfolio
```

The release does not claim an operational:

```text
Parent/Guardian Conference Portfolio
Regulated Portfolio
```

Generic Profile purpose vocabulary is not evidence that those workflows are complete.

## Identity boundary

```text
Portfolio != Portfolio Subject
Portfolio Subject link != institutional/legal identity
Portfolio Subject link != source authorization
Portfolio Subject link != authorship
Portfolio Subject link != contribution
Portfolio Subject link != Score target
```

Cross-class identity uses exact:

```text
school_year + class_id + student_id
```

Display names and bare local student IDs are never identity proof.

## Producer/Candidate boundary

The release preserves:

```text
Core catalog row
    != canonical Core Publication
    != authorized producer read
    != verified producer projection
    != Candidate Evaluation
    != positive Candidate
    != Selection
```

One Candidate identifies one exact representation under one exact Portfolio Subject and
Profile Binding context.

ScoreForm-shaped attempts remain exact independent attempts. Vitrine does not choose:

```text
latest
highest
best
official
Grade-bearing
```

Standards references/alignment do not become proficiency or mastery.

## Collaborative evidence boundary

For Concord-shaped fixtures:

```text
Group Membership
!= Artifact Author
!= Artifact Subject
!= documented contribution
!= represented Group
!= Score target
!= Portfolio Subject
```

A Group Score remains Group-targeted. Vitrine does not individualize it merely because a
Portfolio Subject is a Group member, Artifact Subject, or contributor.

## Curation boundary

```text
Candidate != Selection
Selection Proposal != positive Selection
Selection != Placement
Selection != disclosure authorization
Placement != Arrangement
Reflection != proof of improvement
Curation Review != recipient/disclosure authorization
Composition != Snapshot
```

Current Arrangement and Composition resolve from explicit pointer history rather than
maximum revision or newest timestamp.

## Audience and authorization boundary

V0.2.0 contains bounded `AudienceContext` state and injected authority gates needed for
the local synthetic workflow. It does not implement the complete production privacy
state machine from ADR 0008.

Preserve:

```text
Audience Context != Recipient Scope
Audience Context != source-access authorization
Audience Context != disclosure authorization
Audience Context != consent
actor/role attribution != authority
successful filesystem read != authority
```

Indeterminate/unconfigured authority fails closed.

Production recipient authorization, guardian/relationship evidence, consent,
redaction/de-identification, Disclosure Authorization, delivery, and disclosure logging
remain follow-on work.

## Snapshot and custody boundary

The release keeps these identities separate:

```text
Working Portfolio Composition Revision
Snapshot Build Request
Snapshot Build Plan
Snapshot Build Attempt
Snapshot Build Attempt Result
Snapshot Materialization Record
Snapshot Entry / Omission
internal Snapshot Manifest
Snapshot Seal
Snapshot Edition
Snapshot Current Edition pointer
Snapshot Export Artifact
```

Digest layers remain semantically distinct even if byte values happen to match:

```text
Core producer-manifest digest
producer source digest
acquired-source digest
copied/generated Entry digest
internal Manifest digest
logical inventory digest
Export directory inventory digest
```

Current Edition is determined only through the explicit Snapshot Current pointer. It is
not the numerically greatest Edition. The installed acceptance must retain the case where
Edition 1 is current while Edition 2 is verified and numerically greater.

Issued Editions and verified Exports remain independent of later producer-source drift or
removal.

The internal Snapshot Manifest is not an audience-facing Export member.

## Package-content boundary

The runtime wheel may contain only intended `vitrine/` runtime files, `py.typed`, and
standard distribution metadata.

It must not contain:

```text
tests/
docs/
fixtures/
scripts/
.github/
workspace data
Snapshot output
Export output
sibling PDS package source
pds_core package source
credentials or tokens
cache/build residue
```

The source distribution may contain tests, validators, documentation, and committed
synthetic fixtures required for source qualification.

## Explicitly deferred from v0.2.0

The release does not include:

- live ScoreForm/Quillan/Concord integrations;
- Meridian grading/report integration;
- ordinary Portia Candidate exposure;
- grading, proficiency, mastery, or course Grade calculation;
- production authentication/institutional authorization;
- production recipient/consent/redaction/de-identification workflow;
- external delivery or public hosting;
- operational Parent/Guardian Conference workflow;
- operational regulated Profile/case/checklist/submission workflow;
- NJDOE or other external submission automation;
- Sunset archival/disposition execution;
- web/GUI application;
- 1.0-stable serialized contracts.

Those absences are intentional compatibility boundaries, not permission to use private
fallbacks.
