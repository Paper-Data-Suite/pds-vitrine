# Snapshot, Export, Checksum, and Immutability Contracts

## Status and boundary

This document defines the conceptual Vitrine snapshot architecture for issue #9, **Define snapshot, export, checksum, and immutability contracts**.

It is a foundation design, not a final serialized contract or runtime implementation.

The design defines Vitrine-owned records and invariants for:

- requesting and planning a snapshot from one exact Working Portfolio Composition Revision;
- acquiring exact source representations without following mutable current state;
- copying producer-authorized bytes and rendering structured projections;
- recording every included, reference-only, omitted, unavailable, or failed item;
- hashing copied bytes, generated bytes, manifests, logical inventories, and export containers;
- sealing immutable Snapshot Editions;
- producing several format-specific Export Artifacts from one logical Edition;
- recording issuance, submission, receipt references, lifecycle, and supersession;
- handling build conflicts, partial success, and recovery;
- and preserving exceptional-removal evidence without ordinary hard deletion.

The design does not:

- discover Candidates;
- create or change Selections;
- alter producer-native records;
- implement recipient authorization;
- verify consent or signatures;
- define audience-specific redaction rules;
- send files to external systems;
- calculate Grades or proficiency;
- activate a regulated Profile;
- perform archival disposition;
- or implement executable storage, rendering, or export code.

Those responsibilities remain with the contracts and issues identified below.

## Governing separation

The snapshot model preserves this sequence:

```text
Working Portfolio Composition Revision
  -> Snapshot Build Request
  -> Snapshot Build Plan
  -> Snapshot Build Attempt
  -> Snapshot Entries and Omissions
  -> canonical Snapshot Manifest
  -> Snapshot Seal
  -> immutable Snapshot Edition
  -> one or more Export Artifacts
  -> optional Issuance
  -> optional Submission
  -> optional external Receipt / Outcome reference
```

No arrow is implicit.

The following concepts remain distinct:

```text
Composition Revision
  != Build Request
  != Build Plan
  != Build Attempt
  != Snapshot Edition
  != Snapshot Manifest
  != Snapshot Seal
  != Export Artifact
  != Issuance
  != Submission
  != Delivery
  != Receipt
  != External acceptance
```

Digest claims also remain distinct:

```text
Core producer-manifest digest
  != producer source-artifact digest
  != acquired-source digest
  != copied Snapshot Entry digest
  != generated-entry digest
  != Snapshot Manifest digest
  != logical-inventory digest
  != Export Artifact digest
  != external receipt digest
```

An issued or submitted Edition must never silently:

- refresh from the current Composition pointer;
- follow a newer Candidate Evaluation;
- substitute a successor Candidate;
- follow a newer producer Publication Record;
- replace a selected producer revision;
- use a newer renderer under the same Edition identity;
- change its audience-visible content;
- add newly available content;
- remove content that later becomes unavailable;
- or rewrite its manifest, seal, paths, bytes, or digests.

### Near-term repository direction

The design intentionally anticipates:

- ScoreForm producer-profile registration and Core publication, supersession, and withdrawal;
- Quillan Core 0.6 publication and consumer-neutral student-work and feedback readers;
- Concord Activity workflow, Artifact publication, result manifest, and public Artifact reader;
- Portia coordinated persistence and explicit portfolio-safe projection;
- Meridian grading/report generation and immutable report snapshots;
- Vitrine authorization and redaction work in issue #10;
- regulated Profile packages in issue #11;
- and eventual Sunset archival and disposition integration.

The snapshot contract therefore uses exact module-owned projection references and renderer contracts rather than depending on current private paths or one producer's temporary implementation.

### Reusable cross-repository patterns

The design adopts these suite-wide patterns:

- opaque durable IDs;
- immutable revisions;
- canonical deterministic serialization;
- exact byte hashing with SHA-256;
- exclusive creation rather than overwrite;
- explicit current pointers with expected-predecessor protection;
- source stability checks;
- append-preserving lifecycle and correction;
- structured partial-success outcomes after durability;
- strict regular-file and symlink rejection;
- canonical state independent of derived indexes;
- and exact references that never silently follow successors.

### Incompatible assumptions rejected

The design rejects these assumptions:

- a producer manifest is a Portfolio package;
- a producer work snapshot is a Vitrine Snapshot Edition;
- one PDF or ZIP is the complete logical snapshot model;
- a content hash can replace business identity and lifecycle;
- current source state is safe to dereference during a long build;
- a newer producer source may silently replace an unavailable selected source;
- a package-wide checksum makes per-entry provenance unnecessary;
- an audience label authorizes disclosure;
- an export timestamp is the issuance or submission time;
- successful submission proves receipt or acceptance;
- or local deletion recalls externally distributed copies.

## Authority model

### Vitrine owns

Vitrine owns the canonical snapshot records defined here:

- Snapshot Build Request;
- Snapshot Build Plan;
- Snapshot Build Attempt;
- Snapshot Series;
- Snapshot Edition;
- Snapshot Entry;
- Materialization Record;
- Snapshot Omission;
- Snapshot Manifest;
- Snapshot Seal;
- Snapshot Export Artifact;
- Snapshot Issuance;
- Snapshot Submission;
- Snapshot Lifecycle Event;
- Snapshot Current Pointer;
- and Exceptional Removal Certificate boundary.

### Working Portfolio Composition owns curation input

The exact Working Portfolio Composition Revision remains authoritative for:

- selected Candidate endpoints;
- active Placements and order;
- exact Presentation, Annotation, and Reflection revisions;
- curation findings;
- exact approvals;
- and unresolved obligations.

The snapshot builder does not recalculate or silently update that curation state.

### Producers retain source authority

Producer modules remain authoritative for:

- source identity;
- source revision;
- producer representation identity;
- source bytes or structured projection;
- native lifecycle;
- source correction and withdrawal;
- source digest claims;
- renderer or public-reader behavior owned by the producer;
- and producer privacy classifications.

Vitrine becomes authoritative only for the copied or generated bytes under its custody and for the exact Edition it sealed.

### Core retains publication authority

Core remains authoritative for:

- Publication Records and Withdrawals;
- registration revisions where applicable;
- publication series and supersession;
- producer-manifest paths and SHA-256 bindings;
- compatibility metadata;
- and canonical publication retrieval.

Core does not own Portfolio Snapshot Series, Editions, Entries, Export Artifacts, or Issuance.

### Profiles own policy

The exact bound Portfolio Profile revision defines or references:

- required snapshot purpose;
- permitted audience classes;
- required export formats;
- permitted omission behavior;
- required indexes and appendices;
- review and approval requirements;
- retention references;
- and regulated submission requirements.

A Profile describes policy. It does not create bytes or prove authorization.

### Issue #10 and institutions own disclosure authority

Authentication, authorization, consent, recipient identity, collaborator treatment, redaction approval, audience permission, delivery authorization, and disclosure logging remain issue #10 or institutional responsibilities.

A snapshot record may reference an authorization decision. It does not authenticate or replace it.

### External systems own delivery outcomes

An external system remains authoritative for:

- transmission receipt;
- destination identity;
- delivery status;
- submission tracking;
- external review;
- and external acceptance or rejection.

Vitrine may preserve exact references or imported outcome records without inventing those facts.

## Terminology

### Working Portfolio Composition Revision

One exact immutable, byte-free curation state defined by issue #8.

### Snapshot Build Request

An actor-authored request to build a snapshot from one exact Composition Revision for one purpose and audience-policy context.

### Snapshot Build Plan

An immutable plan that resolves the request to exact source endpoints, materialization operations, expected outputs, required reviews, and permitted omissions.

### Snapshot Build Attempt

One execution attempt against one exact Plan.

### Snapshot Series

A stable Vitrine identity for a logical stream of related immutable Snapshot Editions.

### Snapshot Edition

One immutable logical content edition sealed from one exact Composition Revision and audience-content policy.

### Snapshot Entry

One logical included, reference-only, omitted, unavailable, or failed item considered for the Edition.

### Materialization Record

The provenance of producing one byte-bearing Entry by copying, producer rendering, Vitrine rendering, authorized transformation, or explicit carry-forward.

### Snapshot Manifest

The canonical internal deterministic inventory of the Edition.

### Snapshot Seal

The digest and verification record proving the exact manifest and logical inventory sealed into the Edition.

### Export Artifact

One format-specific immutable realization of an Edition, such as a directory package, ZIP archive, PDF bundle, or HTML package.

### Issuance

An immutable event recording that an authorized actor issued an exact Edition and Export Artifact set for a stated purpose and audience-policy context.

### Submission

An immutable event recording that an exact Edition and Export Artifact set was handed off to a destination or transmission process.

### Exceptional removal

A narrowly authorized removal of locally retained substantive bytes that preserves only minimum lawful identity and integrity evidence.

## Identity conventions

Every canonical snapshot record receives an opaque, non-PII, never-reused ID.

IDs must not encode:

- student name or roster identifier;
- source title;
- class or course;
- producer module;
- audience label;
- lifecycle state;
- file count;
- checksum;
- submission destination;
- or decision outcome.

Snapshot Edition identity is:

```text
snapshot_series_id + positive snapshot_edition
```

The numeric Edition is allocated within one Series. It is not selected as current merely because it is greatest.

A digest must never be the sole business identity. Two separate Editions may legitimately contain identical bytes, and one Edition may have several distinct Export Artifact byte sequences.

## Snapshot Build Request

### Purpose

A Snapshot Build Request records the intent to build from one exact Composition Revision before any source is acquired or bytes are generated.

### Conceptual fields

| Field | Requirement | Meaning |
| --- | --- | --- |
| `snapshot_build_request_id` | Required | Opaque durable Request identity. |
| `contract_version` | Required | Request contract version. |
| `portfolio_id` | Required | Exact Portfolio. |
| `portfolio_subject_id` | Required | Exact Portfolio Subject. |
| `profile_binding_id` | Required | Exact Profile Binding. |
| `portfolio_profile_id` | Required | Stable Profile series snapshot. |
| `profile_revision` | Required | Exact Profile revision. |
| `composition_revision_id` | Required | Exact Working Portfolio Composition Revision. |
| `snapshot_purpose` | Required | Purpose declared by the Profile or permitted local policy. |
| `audience_policy_reference` | Required | Exact audience-content policy reference; not authorization. |
| `requested_export_formats` | Required | Ordered unique requested format and contract pairs. |
| `requester` | Required | Exact actor reference. |
| `asserted_role` | Required | Role used to request the build. |
| `requested_at` | Required | Aware timestamp. |
| `review_references` | Optional | Exact curation review decisions available at request time. |
| `authorization_references` | Optional | Exact external or issue #10 decision references available at request time. |
| `idempotency_key` | Optional | Caller-supplied retry key scoped to the Portfolio and purpose. |
| `predecessor_request_id` | Optional | Earlier Request intentionally replaced or revised. |

### Validation

A Request is structurally valid only when:

- the Portfolio, Subject, Profile Binding, and Composition Revision match;
- the Composition Revision is complete enough for request planning;
- every requested format is permitted or conditionally permitted by the exact Profile;
- the audience-content policy exists;
- the requester role is syntactically valid;
- and predecessor relationships are acyclic.

A valid Request may still be unauthorized or unbuildable.

### Forbidden fields

A Request must not contain:

- copied source bytes;
- mutable source paths;
- a claim that the audience is authorized;
- generated output digests;
- issuance or submission time;
- external acceptance;
- or a mutable `completed` Boolean.

### Entry Plan

Each Entry Plan should preserve:

- exact Selection and Placement references;
- exact Candidate and Candidate Evaluation;
- exact producer projection and revision;
- expected acquisition mode;
- expected source digest claim where available;
- output semantic role;
- normalized target relative path;
- renderer or materializer contract;
- audience-content inclusion rule;
- required review gates;
- and permitted failure or omission outcomes.

### Frozen endpoint rule

After a Plan is finalized, execution must not consult mutable current pointers to choose a different:

- Composition Revision;
- Candidate Evaluation;
- producer Publication;
- source representation;
- renderer version;
- Profile revision;
- audience-content policy;
- or expected output path.

A material change requires a successor Plan and a new Build Attempt.

| `generation_outcomes` | Required | Exact generated-entry outcomes. |
| `export_outcomes` | Optional | Export generation outcomes. |

| `snapshot_series_id` | Optional | Allocated Series when known. |

### Attempt allocation

Attempt numbers may be consumed by failures.

Snapshot Edition numbers must not be consumed unless a durable immutable Edition reached the sealing boundary. If an exclusive Edition target was created but final durability cannot be established, the result is an integrity or partial-success condition requiring conservative recovery rather than number reuse.

### Failure retention

Failed Attempts are canonical process history. They may contain privacy-minimized diagnostics, but not copied educational content in ordinary logs.

| `created_at` | Required | Creation time. |

### Series boundary

A new Series is normally required when the logical stream changes materially, including:

- a different Portfolio or Subject;
- a different snapshot purpose;
- a materially different audience-content policy;
- an unrelated regulated submission program;
- or a Profile migration that cannot preserve comparable Series semantics.

A successor Profile Binding may remain in the same Series only through an explicit migration decision preserving the Series purpose and audience-content policy.

### Edition immutability

After durable sealing, the Edition's:

- identity;
- Composition input;
- Entry inventory;
- Omissions;
- manifest bytes;
- seal;
- and logical-content policy

must never be overwritten or revised in place.

A changed audience-visible byte sequence creates a new Edition.

### Identical content

Two Editions may have identical manifest or Entry digests when they represent separate business events, such as a separately approved reissuance or migration. Identity and lifecycle remain separate from byte equality.

### One logical item, several byte entries

A selected item may legitimately produce several Entries when the policy requires separate representations, such as:

- original work PDF;
- accessible text derivative;
- teacher feedback PDF;
- student Reflection;
- and a thumbnail.

Each byte sequence receives its own Entry identity and digest.

### Forbidden fields

An Entry must not contain:

- absolute paths;
- secret destination credentials;
- mutable source-current pointers;
- a claim that a digest is a digital signature;
- producer-private data outside the approved projection;
- or a mutable `latest` flag.

## Digest model

### Initial algorithm

The initial required algorithm is lowercase hexadecimal SHA-256.

The contract should permit future algorithms only through explicit versioned support, never silent substitution.

### Digest layers

| Layer | What it proves | What it does not prove |
| --- | --- | --- |
| Core producer-manifest digest | Exact producer manifest bytes bound by a Core Publication Record. | Source artifact bytes, copied Entry bytes, Portfolio eligibility, or authorization. |
| Producer source-artifact digest | Exact producer-owned artifact bytes where the producer supplies a claim. | That Vitrine read or copied those bytes successfully. |
| Acquired-source digest | Exact bytes Vitrine read from the guarded source boundary. | That output storage contains the same bytes. |
| Snapshot Entry digest | Exact copied or generated Entry bytes under Vitrine custody. | Logical Edition identity, audience authorization, or package delivery. |
| Snapshot Manifest digest | Exact canonical internal manifest bytes. | Export container bytes or external receipt. |
| Logical inventory digest | Contract-defined Entry inventory independent of container metadata. | Complete internal provenance unless defined by the projection. |
| Export Artifact digest | Exact ZIP, PDF, HTML archive, or other artifact bytes. | Logical equality with another format or external acceptance. |
| External artifact digest | Exact imported receipt or decision bytes. | Authenticity unless the external signature/verification contract proves it. |

### Equal digest values

When two layers happen to have the same digest, they remain separate claims with separate authorities.

For example, an exact byte copy may make acquired-source and Snapshot Entry digest values equal. The manifest must still record each claim and meaning independently.

### No security overclaim

A checksum detects byte changes under the assumed digest algorithm.

It is not by itself:

- an electronic signature;
- identity proof;
- authorization;
- nonrepudiation;
- encryption;
- access control;
- or proof of lawful disclosure.

## Logical Edition versus Export Artifact

The logical Edition contains the authoritative ordered inventory of content and omissions.

Export Artifacts are format-specific realizations.

This permits:

- one Edition with a directory package and ZIP archive;
- one Edition with a PDF bundle and accessible HTML package;
- independent export validation and digesting;
- regeneration under a successor export contract without rewriting the Edition;
- and precise identification of the bytes actually issued or submitted.

A format that cannot faithfully represent all required Edition content must fail or declare a policy-permitted excluded Entry set. It must not silently drop content.

## Source acquisition rules

### Exact source endpoint

Each source acquisition begins from the exact source representation fixed in the Build Plan.

The builder must not choose a source using:

- a producer current pointer;
- greatest revision;
- newest timestamp;
- matching filename;
- latest attempt;
- or search by title.

### Guarded byte acquisition

For producer-authorized source bytes, an eventual implementation should:

1. resolve the exact approved source endpoint;
2. reject URL-like paths where local paths are required;
3. reject absolute paths and containment escape;
4. reject symlinks, junctions, and nonregular files;
5. open through a guarded binary boundary;
6. read immutable bytes;
7. hash the exact bytes read;
8. verify the producer digest claim where available;
9. copy to an exclusive staging target;
10. flush and sync where supported;
11. reload and independently hash staged output;
12. verify source stability where the source contract permits;
13. and preserve a Materialization Record.

Metadata equality alone is insufficient to prove stability.

### Structured projection acquisition

A structured producer projection must be validated by the exact producer public reader before Vitrine renders it.

The renderer input reference must bind:

- projection kind;
- projection contract;
- exact source identity;
- exact source revision;
- and a canonical input digest or equivalent immutable projection fingerprint.

### Producer render

A producer-rendered output is acquired through the producer's exact public renderer contract. Vitrine records producer renderer identity and output digest without claiming the output is a native source artifact.

### Vitrine render

Vitrine may render:

- curator presentations;
- annotations;
- reflections;
- cover pages;
- indexes;
- and approved structured producer projections.

The render contract must not broaden producer fields or reinterpret native semantics.

### Prior-snapshot carry-forward

Carrying forward prior Entry bytes is allowed only when:

- the exact Profile and audience-content policy permit it;
- the Build Plan names the exact prior Entry;
- the prior Entry and Edition validate successfully;
- the original producer provenance remains preserved;
- the Materialization Record states `prior_snapshot_copy`;
- and the new Edition does not claim fresh source verification.

Silent cache fallback is prohibited.

### Source mutation during build

When source bytes or source state change after planning, the builder must:

- fail with a conflict;
- create a successor Plan;
- record a policy-permitted Omission;
- or intentionally use an approved prior-snapshot carry-forward.

It must not substitute current data automatically.

## Build, staging, sealing, and durability protocol

### Phase 1: load immutable inputs

The builder loads and validates:

- exact Build Request;
- exact Build Plan;
- exact Composition Revision;
- exact Profile Binding;
- exact approval and authorization references required for build;
- and exact source endpoints.

The builder does not re-resolve the Composition Current Pointer after planning.

### Phase 2: create exclusive staging scope

The builder creates a noncanonical staging directory or equivalent transaction scope identified only by the Build Attempt.

Staging must:

- be outside sealed Edition paths;
- reject preexisting untrusted content;
- reject symlinks and junctions;
- use exclusive file creation;
- and be safe to remove when no durable Edition exists.

### Phase 3: materialize Entries

Each planned Entry receives one terminal acquisition outcome:

```text
included
reference_only
omitted_permitted
failed_blocking
```

The attempt must not infer success from file existence alone.

### Phase 4: generate indexes and manifests

After all source Entries are stable, Vitrine generates:

- audience-safe indexes and appendices;
- internal Omission records;
- the deterministic internal Snapshot Manifest;
- and the logical inventory projection where used.

### Phase 5: verify complete staging state

Final staging verification must:

- reload every byte-bearing Entry;
- rehash every Entry;
- validate size and media type;
- validate unique normalized paths;
- validate all Materialization Records;
- validate all Omissions and their sealing permission;
- verify the manifest references exactly the staged inventory;
- calculate the manifest digest;
- calculate the logical inventory digest where used;
- and confirm the exact Composition and Plan bindings.

### Phase 6: publish immutable Edition

The Edition target is created exclusively and published atomically or through an equivalently guarded commit protocol.

The implementation must never:

- overwrite an existing Edition;
- merge into a partially existing sealed directory;
- trust a mutable alias as canonical content;
- or reuse an Edition identity after uncertain durability.

### Phase 7: publish current pointer separately

Sealing an Edition does not automatically make it current unless the policy and operation explicitly update the Snapshot Current Pointer.

The pointer update uses expected-predecessor protection. Pointer-update failure does not invalidate the already sealed Edition.

### Phase 8: optional Export Artifacts

Required Export Artifacts may be part of the sealing gate when the Profile says the Edition is incomplete without them.

Optional Export Artifacts may be created after sealing. Their failure creates a structured partial-success or export-failure outcome without deleting the Edition.

## Exact replay and idempotency

### Request retry

A repeated idempotency key with an exactly equal canonical Request may return the existing Request identity.

The same key with different content is a conflict.

### Plan replay

A Plan may be replayed only when all exact inputs and plan fingerprint remain valid.

If source availability or authorization changes, replay may fail even though the Plan remains historical.

### Edition replay

A repeated build operation may return an existing sealed Edition only when the caller explicitly requests replay and the exact Request, Plan, Composition, audience-content policy, Entry inventory, Omissions, manifest bytes, and Seal are identical.

The implementation must not touch sealed files or update timestamps during replay.

### Export replay

An Export Artifact may be replayed only against the same Edition and exact export contract and configuration. The existing artifact bytes are returned unchanged.

## Partial-success model

### Before sealing

Before durable sealing, failures normally produce:

- a failed Build Attempt;
- no Snapshot Edition;
- removable staging output;
- and structured cleanup records when cleanup fails.

### After sealing

After durable sealing, the Edition is immutable and must be preserved even when:

- current-pointer update fails;
- lock cleanup fails;
- staging cleanup fails;
- derived catalog rebuild fails;
- optional Export Artifact generation fails;
- optional thumbnail generation fails;
- or routine post-seal verification reporting fails after the seal itself was already durably established.

The result is `partial_success_after_seal` with exact Edition identity and warning records.

### Uncertain durability

When the implementation cannot determine whether a target became durable, it must fail conservatively:

- do not reuse the Edition number;
- quarantine or inspect the target;
- do not declare success;
- and require explicit recovery.

## Unavailable, withdrawn, and retired sources

### Source unavailable before planning

The planner records an unavailable source and applies exact Profile omission policy.

It must not create a plan that claims an exact copy will occur unless an approved alternative, such as prior-snapshot carry-forward, is named.

### Source unavailable after planning

The Attempt records an acquisition failure. Sealing is allowed only when the exact planned omission policy permits conversion to an Omission.

### Source withdrawn

A producer or Core withdrawal does not erase historical source identity.

The build policy must decide whether:

- historical use remains permitted;
- a prior-snapshot carry-forward is permitted;
- an Omission is permitted;
- or the build must fail.

The builder must not silently follow a successor Publication.

### Projection retired

A retired producer projection contract may remain readable for historical verification while being prohibited for new builds.

That policy state must be explicit. Runtime inability to read the contract is distinct from policy retirement.

### Source corrected after sealing

A source correction after sealing may trigger:

- a new Candidate and Selection review;
- a successor Composition Revision;
- a successor Snapshot Edition;
- lifecycle invalidation or revocation of the old Edition;
- or no action when the earlier Edition remains historically accurate for what was issued.

It never edits the old Edition.

## Audience-content policy

### Audience class versus audience-content policy

An audience class is a policy label such as:

```text
student
teacher
family
internal_reviewer
external_reviewer
public
regulated_authority
```

An audience-content policy is an exact versioned rule set defining what content, metadata, notices, and transformations the package contains.

Two audiences may share a content policy, and one audience class may have several policy revisions.

### Authorization remains separate

The presence of an audience-content policy does not establish that any recipient may receive the Edition.

Issue #10 must later resolve:

- exact recipient scope;
- actor authorization;
- consent;
- collaborator treatment;
- disclosure limitations;
- redaction approval;
- and delivery logging.

### Content changes require a new Edition

A new Edition is required when audience policy changes any visible:

- Entry;
- title or caption;
- Annotation or Reflection;
- provenance detail;
- omission notice;
- collaborator identity;
- redaction;
- accessibility derivative;
- or language presentation.

A mere container change does not require a new Edition when logical content remains identical.

## Conceptual persistence layout

The final implementation may choose another validated layout, but the design expects separation similar to:

```text
portfolios/<portfolio_id>/
  snapshots/
    series/<snapshot_series_id>/
      editions/<snapshot_edition>/
        manifest.json
        seal.json
        entries/...
      exports/<snapshot_edition>/<export_artifact_id>/...
      current.json
    build_requests/...
    build_plans/...
    build_attempts/...
    issuance/...
    submissions/...
```

Requirements:

- canonical paths are deterministic from opaque IDs, not titles;
- sealed Edition paths are immutable;
- staging is separate;
- current pointers are separate objects;
- export artifacts cannot overwrite Edition content;
- derived catalogs are outside canonical reconstruction requirements;
- and no audience package path may expose sensitive semantic identifiers.

The path sketch is conceptual and does not establish final filesystem API.

## Integrity validation

Validation should be layered.

### Structural validation

Checks exact fields, closed vocabularies, types, normalized paths, and digest syntax.

### Reference validation

Checks exact existence and scope of:

- Portfolio;
- Subject;
- Profile Binding;
- Composition Revision;
- Candidate and producer source;
- Entries and Materialization Records;
- Edition and Export Artifacts;
- Issuance and Submission targets;
- and predecessor/successor relationships.

### Inventory validation

Checks:

- complete expected Entry disposition;
- unique paths;
- digest and size agreement;
- manifest inventory equality;
- logical inventory digest;
- and omission policy.

### Lifecycle validation

Checks:

- one initial seal;
- valid supersession targets;
- no replacement cycles;
- pointer target eligibility;
- issuance and submission restrictions after withdrawal, invalidation, or removal;
- and explicit authorization for revocation or exceptional removal.

### Storage validation

Checks:

- regular nonsymlink files;
- containment;
- canonical serialization;
- immutable sealed paths;
- complete Edition chain where required;
- and absence of unreferenced canonical objects.

### Derived integrity findings

Integrity findings may be deterministic rebuildable projections rather than canonical lifecycle records.

A finding clears only when reevaluation no longer detects it. It must not silently repair sealed content.

## Required edge-case behavior

### Current Composition advances during build

The build continues against the exact planned Composition Revision. It does not refresh.

### Candidate Current Pointer advances

The selected Candidate and Candidate Evaluation remain those referenced by the Composition. No substitution occurs.

### Source Publication is superseded

The exact source remains the planned endpoint. Policy determines historical use, omission, or failure. The builder does not follow the successor.

### Source bytes change during read

The Attempt fails with a source-mutation conflict unless an exact source contract provides another safe immutable retrieval mechanism.

### Required item unavailable

Sealing fails unless the exact Profile and audience-content policy permit an Omission.

### Optional item unavailable

A permitted Omission is recorded with correct audience notice policy.

### Internal manifest contains restricted provenance

The manifest remains internal. The audience package contains only a separately generated allowlisted provenance appendix where required.

### ZIP export fails after Edition sealing

The Edition remains valid. A required-format failure may block Issuance; an optional-format failure is structured partial success.

### Seal succeeds but lock cleanup fails

The Edition remains allocated and immutable. The Attempt reports partial success and exact cleanup diagnostics.

### Two builders target the same Edition

Exclusive creation permits one durable winner. The other fails or exact-replays only after verifying complete equality.

### Source corrected after issuance

The old Edition and Issuance remain historical. Policy may invalidate or revoke future use and create a successor Edition.

### Exceptional local removal

The removal certificate and lifecycle event remain. Vitrine does not claim external copies were erased.

## Invariants

1. One Build Plan binds one exact Composition Revision.
2. Build execution never silently dereferences current Composition state.
3. Snapshot Series and Snapshot Edition are distinct.
4. Snapshot Edition and Export Artifact are distinct.
5. Edition identity is not derived solely from a digest.
6. Different audience-visible content requires a new Edition.
7. Different containers may realize one Edition.
8. Every byte-bearing Entry has an independent digest and size.
9. Every byte-bearing Entry has a Materialization Record.
10. Producer source digest claims and Vitrine output digests remain distinct.
11. The producer manifest digest is never reused as proof of copied Portfolio bytes.
12. Every planned item receives a terminal included, reference-only, omitted, or blocking-failure outcome.
13. A required unpermitted omission blocks sealing.
14. Suppressed sources do not leak through audience output.
15. The internal manifest is not automatically distributed.
16. The Snapshot Manifest has deterministic canonical bytes.
17. The manifest does not contain its own digest field.
18. The Seal binds the exact manifest after final verification.
19. Sealed Edition paths are never overwritten.
20. Failed staging is not a Snapshot Edition.
21. Durable post-seal partial success preserves the Edition.
22. Uncertain durability never permits Edition-number reuse.
23. Source changes never silently refresh an Edition.
24. Candidate or Publication successors never silently replace selected sources.
25. Renderer changes never modify a sealed Edition.
26. Prior-snapshot carry-forward is explicit and attributable.
27. Current Edition uses an explicit guarded pointer.
28. Greatest Edition number and newest timestamp do not define current state.
29. Supersession, withdrawal, invalidation, and revocation preserve predecessor history.
30. Issuance and Submission bind exact Export Artifacts.
31. Build, seal, export, issue, submit, receive, and decide times remain distinct.
32. Export success does not establish delivery, receipt, or acceptance.
33. Audience-content policy does not establish recipient authorization.
34. Exceptional removal is not an ordinary workflow.
35. Local removal does not claim recall of external copies.
36. Producer-native records are never made Vitrine-owned by copying.
37. ScoreForm attempt choice remains separate from grading policy.
38. Quillan private records remain inaccessible.
39. Concord work snapshots remain producer state, not Portfolio Editions.
40. Portia source suppression remains intact.
41. Meridian report snapshots retain Meridian identity.
42. Derived indexes are rebuildable and nonauthoritative.
43. No sibling repository is modified by this design.
